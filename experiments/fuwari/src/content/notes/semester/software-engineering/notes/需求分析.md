## 一、需求分类（必考辨析）

| 分类 | 英文 | 定义 | 示例 |
|------|------|------|------|
| **业务需求** | Business Requirement | 组织的高层次目标需求 | "提高客户管理效率 30%" |
| **用户需求** | User Requirement | 用户使用系统需要完成的任务 | "用户可以查看订单状态" |
| **功能需求** | Functional Requirement | 系统必须提供的具体功能 | "系统应支持按日期范围查询订单" |
| **非功能需求** | Non-functional Requirement | 系统性能、安全等质量约束 | "响应时间 < 2 秒，支持 1000 并发" |

> 🔑 **辨析口诀**：业务求目标、用户求场景、功能求能力、非功能求品质。

<div id="section-2" class="note-anchor"></div>

### 非功能需求的细分

| 子类 | 说明 | 示例 |
|------|------|------|
| **性能需求** | 响应时间、吞吐量、并发量 | 查询响应 < 1s |
| **可靠性** | MTBF（平均无故障时间）、可用性 | 99.9% uptime |
| **安全性** | 权限控制、数据加密、防攻击 | 密码必须加密存储 |
| **可用性/易用性** | 用户界面的直观性 | 新用户 5 分钟内完成基本操作 |
| **可维护性** | 模块化、可扩展性 | 新增支付渠道 ≤ 3 人天 |
| **可移植性** | 跨平台能力 | 支持 Windows/Linux/macOS |

## 二、需求工程的主要活动

```
需求开发                   需求管理
├── 需求获取              ├── 需求变更控制
├── 需求分析              ├── 需求版本控制
├── 需求规格说明（SRS）    └── 需求状态跟踪
└── 需求验证/审查
```

<div id="section-4" class="note-anchor"></div>

### 2.1 需求获取方法（常考选择题）

| 方法 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| **访谈法** | 一对一/一对多当面交流 | 深入、可追问 | 耗时、覆盖面有限 |
| **问卷调查** | 发放结构化问卷 | 覆盖面广、量化 | 回收率不确定、不够深入 |
| **座谈会** | 组织用户集体讨论 | 多视角碰撞 | 可能被少数人主导 |
| **原型法** | 快速构建原型供用户试用 | 直观澄清需求 | 可能被误认为成品 |
| **头脑风暴** | 自由发散提出想法 | 创意丰富 | 需要好的引导 |
| **现场观摩** | 到用户实际工作现场观察 | 发现隐性需求 | 耗时 |

<div id="section-5" class="note-anchor"></div>

### 2.2 需求分析步骤

> 老师 PPT 原文：**分解 → 提炼 → 消除矛盾**

| 步骤 | 说明 |
|------|------|
| 分解 | 将复杂需求拆分为可管理的子需求 |
| 提炼 | 从模糊、冗余的信息中提取本质需求 |
| 消除矛盾 | 识别并解决不同干系人之间的需求冲突 |

## 三、需求规格说明书（SRS）

> SRS（Software Requirements Specification）是需求阶段的**核心产出物**。

<div id="section-7" class="note-anchor"></div>

### SRS 的定义

> SRS 是精确、完整地描述系统**"做什么"**（WHAT）的正式文档，**不**描述"怎么做"（HOW）。

<div id="section-8" class="note-anchor"></div>

### SRS 应具备的特征（必考多选）

| 特征 | 说明 |
|------|------|
| **正确性** | 每个需求都是系统应该满足的 |
| **无歧义性** | 每个需求只有唯一的解释 |
| **完整性** | 涵盖所有必需的功能和约束 |
| **一致性** | 需求之间没有冲突 |
| **可验证性** | 存在可量化方式验证需求是否满足 |
| **可修改性** | 可以方便地修改而不破坏结构 |
| **可追踪性** | 能追溯需求的来源和实现 |
| **可理解性** | 所有干系人都能读懂 |

> **记忆口诀**：无歧义、完整、可验证、一致、可修改、可追踪

<div id="section-9" class="note-anchor"></div>

### 不应该出现在 SRS 中的内容

| 不应出现的内容 | 原因 | 应该出现在哪里 |
|----------------|------|----------------|
| 系统实现算法 | SRS 只描述 WHAT | 设计文档（SDD） |
| 数据库表结构设计 | 属于详细设计 | 设计文档 |
| 编程语言/框架选择 | 属于技术选型 | 设计文档或技术方案 |
| 测试计划和用例 | 属于测试文档 | 测试计划文档 |

## 四、需求跟踪矩阵

> 需求跟踪矩阵（RTM）用于建立需求的**双向追踪**。

| 追踪方向 | 说明 |
|----------|------|
| **前向追踪**：需求 → 设计 → 编码 → 测试 | 确保每个需求都有实现 |
| **后向追踪**：测试 → 编码 → 设计 → 需求 | 确保每个实现都对应合理需求 |

## 五、传统需求分析方法（了解）

| 方法类型 | 模型/工具 | 说明 |
|----------|-----------|------|
| **数据模型**（静态） | ER 图、数据字典 | 描述系统涉及的数据及其关系 |
| **功能模型**（静态） | 数据流图（DFD） | 描述数据如何在系统中流动和变换 |
| **行为模型**（动态） | 状态转移图、状态图 | 描述系统如何响应外部事件 |

> 这是**面向过程**的分析方法，考试一般只要求了解与面向对象方法的区别。

## 期末考试常见考点

<div id="section-13" class="note-anchor"></div>

### 简答题

> **Q：功能需求与非功能需求有什么区别？各举例说明。**
>
> **答题要点**：
> 1. 功能需求描述系统"做什么"——具体的功能行为，如"用户可以查询订单"
> 2. 非功能需求描述系统"做得如何"——质量约束，如"查询响应时间 < 1 秒"
> 3. 功能需求可通过具体功能实现来验证，非功能需求需要性能测试等量化手段验证

<div id="section-14" class="note-anchor"></div>

### 选择题/判断题

> **判断题：需求规格说明书（SRS）应该包含系统实现的核心算法。**
>
> **答案：❌ 错误**。SRS 只描述 WHAT，不描述 HOW。算法属于设计文档范围。

> **判断题："系统应支持支付宝支付"是功能需求，"系统应在 2 秒内完成支付处理"是非功能需求。**
>
> **答案：✅ 正确**。
