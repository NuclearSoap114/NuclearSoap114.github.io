## 一、模型全景对比表

| 维度 | 瀑布模型 | V 模型 | 原型模型 | 增量模型 | 螺旋模型 |
|------|----------|--------|----------|----------|----------|
| **开发方式** | 线性顺序 | V 字形顺序 | 先快速构建原型 | 逐模块增量交付 | 循环迭代 |
| **阶段回溯** | ❌ 不可回溯 | ❌ 不可回溯 | ✅ 原型→反馈→修正 | ✅ 逐增量反馈 | ✅ 每轮评审 |
| **用户参与** | 仅首尾 | 主要在首尾 | 原型评审阶段参与 | 每个增量发布后参与 | 每轮迭代末参与 |
| **文档量** | 重 | 重 | 中 | 中 | 中 |
| **风险管理** | 几乎无 | 较低 | 低 | 逐增量处理 | **核心特征**（显式风险分析） |
| **测试介入** | 最后阶段 | **与开发并行**（对应关系） | 原型验证 | 每个增量完成后 | 每轮结束后 |
| **灵活性** | ❌ 极低 | ❌ 较低 | ✅ 高 | ✅ 较高 | ✅ 中等 |
| **适用场景** | 需求明确且稳定 | 安全关键系统 | 需求模糊、UI 密集 | 需快速交付核心功能 | 大型/复杂/高风险 |
| **典型应用** | 传统 MIS 系统 | 航空航天、医疗设备 | 新产品概念验证 | 电商平台分期上线 | 国防、航天系统 |

## 二、各模型详解

<div id="section-3" class="note-anchor"></div>

### 2.1 瀑布模型（Waterfall Model）

```
需求分析 → 设计 → 编码 → 测试 → 维护
（自上而下，不能回溯）
```

| 优点 | 缺点 |
|------|------|
| 阶段清晰，便于分工管理 | 缺乏灵活性，变更成本极高 |
| 强制要求文档交付 | 用户只能最后看到成品 |
| 适合需求稳定的项目 | 缺陷发现晚（测试在最后） |

**变体**：

- **带反馈环的瀑布模型**：相邻阶段间增加反馈箭头，一定程度上缓解不可回溯问题
- **V 模型**（详见下方）

---

<div id="section-4" class="note-anchor"></div>

### 2.2 V 模型（Verification & Validation Model）

> 强调**测试与开发并行**，每个开发阶段对应一个测试阶段。

```
需求分析 ←————→ 验收测试
   ↓               ↑
概要设计 ←————→ 系统测试
   ↓               ↑
详细设计 ←————→ 集成测试
   ↓               ↑
  编码  ←————→  单元测试
```

| 优点 | 缺点 |
|------|------|
| 测试与开发并行，早期介入验证 | 仍是顺序模型，灵活性差 |
| 每个阶段有明确的验证目标 | 不适合需求频繁变化的项目 |

> 🔑 **V 模型核心考点**：体现了"尽早测试"原则。左边是验证（Verification——做对了事吗？），右边是确认（Validation——做了对的事吗？）。

---

<div id="section-5" class="note-anchor"></div>

### 2.3 原型模型（Prototype Model）

> 快速构建一个**可运行的样机**，帮助用户澄清和确认需求。

```
快速需求分析 → 构建原型 → 用户试用/反馈 → 修改原型 → ... → 最终产品
```

| 优点 | 缺点 |
|------|------|
| 减少需求不确定性 | 原型可能被误认为就是成品 |
| 用户能"看到"未来系统 | 可能过早关注界面细节而忽略架构 |
| 适用于需求模糊的项目 | 原型代码通常质量低，不适合直接演进 |

---

<div id="section-6" class="note-anchor"></div>

### 2.4 增量模型（Incremental Model）

> 将系统划分为多个**增量（构建）**，每个增量经历完整瀑布周期，逐个交付。

```
增量1: 需求→设计→编码→测试 → 交付核心功能
增量2: 需求→设计→编码→测试 → 交付功能扩展
增量3: ...
```

| 优点 | 缺点 |
|------|------|
| 逐步交付可用软件，客户能及早看到成果 | 需要良好的前期架构设计（开放性） |
| 每个增量可获取用户反馈 | 总开发成本可能高于瀑布 |
| 降低技术风险 | 增量边界划分困难 |

> 🔑 与原型模型的区别：原型模型追求"快速验证想法"，原型通常丢弃；增量模型每个增量都是**交付产品的真实部分**。

---

<div id="section-7" class="note-anchor"></div>

### 2.5 螺旋模型（Spiral Model）

> **Boehm 提出**，核心特征是**显式风险分析**。每轮螺旋包含 4 个象限。

```
       规划
      /   \
   评审 — 风险分析（核心！）
      \   /
       工程实施
```

| 象限 | 任务 |
|------|------|
| **规划** | 确定目标、方案、约束 |
| **风险分析** | 评估风险、制定化解措施 |
| **工程实施** | 开发与测试（原型/瀑布/增量均可） |
| **客户评审** | 评审结果，决定是否进入下一轮 |

| 优点 | 缺点 |
|------|------|
| **显式风险管理**，适合高风险项目 | 复杂、昂贵 |
| 结合了原型/瀑布/增量的优点 | 需要专业风险评估人员 |
| 适用于大型复杂系统 | 中小项目过于沉重 |

## 三、情景判断题（考试高频）

> 给定一个项目情景，让你选择最合适的开发模型。

| 情景 | 推荐模型 | 判断依据 |
|------|----------|----------|
| 需求清晰稳定，中小型 MIS 系统 | **瀑布模型** | 流程简单，阶段明确，需求不变 |
| 用户说不清需求，需"先看看效果" | **原型模型** | 快速建模澄清需求 |
| 需要尽快推出核心功能抢占市场 | **增量模型** | 先交付 MVP，后续增量扩展 |
| 大型国防/航天系统，技术/安全风险高 | **螺旋模型** | 显式风险分析每轮化解风险 |
| Web/移动端创业项目，需求频繁变化 | **敏捷开发**（见下一章） | 灵活性最高，快速迭代 |
| 医疗设备/飞行控制系统（安全关键） | **V 模型** | 测试与开发严格对应 |

## 四、记忆口诀

| 模型 | 核心关键词 | 一句话 |
|------|------------|--------|
| 瀑布 | 线性不可回溯 | 一步一步往下走，不回头 |
| V 模型 | 测试与开发对应 | 左边开发，右边对应测试 |
| 原型 | 快速建模 | 先做个样子给用户看 |
| 增量 | 逐个交付 | 一块一块做好，逐步交付 |
| 螺旋 | **风险分析** | 每轮都要评估风险再动手 |

## 期末考试常见考点

<div id="section-11" class="note-anchor"></div>

### 简答题

> **Q：比较瀑布模型和增量模型的优缺点，并说明各自的适用场景。**
>
> **答题要点**：
> 1. 瀑布：线性顺序、阶段清晰、文档完备，但灵活性差、后期才能发现缺陷。适用：需求明确稳定的中小型项目。
> 2. 增量：逐模块交付、用户可见进度、能获取反馈，但需要良好的架构设计。适用：需快速交付核心功能、需求大体明确的项目。
> 3. 结论：需求稳定选瀑布，需要迭代反馈选增量。

> **Q：螺旋模型的最大特点是什么？为什么它适用于高风险项目？**
>
> **答题要点**：
> 1. 最大特点：**显式的风险分析**（每个螺旋周期包含专门的"风险分析"象限）
> 2. 原因：高风险项目存在大量不确定性（技术、需求、安全等），螺旋模型在每轮迭代中都先识别风险、评估风险、制定化解措施，从而在早期将风险消除或降到可控范围
