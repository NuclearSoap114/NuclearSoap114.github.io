> **一句话理解**
> 当一个算法反复做：
>
> **枚举大量候选 → 判断某个属性是否满足条件 → 累加结果**
>
> 可以考虑把候选提前按照这个属性分类，并维护它们的统计信息。
>
> 于是：
>
> `枚举 + 判断`
>
> 可以优化成：
>
> `直接查询`

---

### 1. 什么是“聚合”

假设有很多状态 `j`，每个状态都有一个属性：

```text
property[j]
````

现在对于每个状态 `i`，都需要计算：

```
for(int j : candidate){
    if(property[j] == need){
        dp[i] += dp[j];
    }
}
```

这里真正需要的信息其实不是：

> 哪些 `j` 满足条件？

而是：

> 所有 `property[j] == need` 的 `dp[j]` 加起来是多少？

于是可以提前维护：

```
sum[x]
```

表示：

```
property[j] == x 的所有 dp[j] 之和
```

那么转移直接变成：

```
dp[i] += sum[need];
```

状态 `j` 算出来后：

```
sum[property[j]] += dp[j];
```

这就是最基本的**按属性聚合**。

---

## 2. 为什么它能优化复杂度

原来的暴力结构：

```
for(int i=1;i<=n;i++){
    for(int j=1;j<=n;j++){
        if(property[j] == need[i]){
            dp[i] += dp[j];
        }
    }
}
```

最坏复杂度：

\[ O(n^2) \]

但如果维护：

```
sum[property]
```

就变成：

```
for(int i=1;i<=n;i++){
    dp[i] += sum[need[i]];
    sum[property[i]] += dp[i];
}
```

如果数组可以直接索引：

\[ O(n) \]

如果使用 `map`：

\[ O(n\log n) \]

如果使用 `unordered_map`：

\[ 平均\ O(n) \]

所以它真正优化掉的是：

> **每次查询时重新寻找满足条件的状态。**

---

## 3. 聚合思想的本质

暴力：

```
需要答案
   ↓
重新扫描所有候选
   ↓
找到符合条件的
   ↓
计算答案
```

聚合：

```
状态产生
   ↓
按照属性分类保存
   ↓
以后需要时直接取出
```

换句话说：

> **把查询时的工作，提前转移到状态产生的时候完成。**

这是一个非常通用的算法思想。

---

## 4. 最重要的问题：到底按照什么属性聚合？

这是聚合优化中最关键的一步。

不要问：

> 当前状态有什么属性？

而应该问：

> **未来查询时，我是按照什么条件找它的？**

比如未来的查询是：

```
if(value[j] == x)
```

那么可以考虑：

```
sum[x]
```

如果查询是：

```
if(color[j] == c)
```

可以考虑：

```
sum[c]
```

如果查询是：

```
if(type[j] == t && color[j] == c)
```

可以考虑：

```
sum[t][c]
```

或者：

```
map<pair<int,int>,int> sum;
```

因此可以记一个非常重要的原则：

> [!important] 聚合状态设计原则  
> **从未来的查询条件反推当前应该存到哪个 key。**

# 5. 常见的聚合类型

聚合并不一定是求和。

---

## 5.1 求和聚合

暴力：

```
for(int j : candidate){
    if(property[j] == x){
        dp[i] += dp[j];
    }
}
```

优化：

```
dp[i] += sum[x];
```

维护：

```
sum[property[i]] += dp[i];
```

适用于：

- 统计方案数
- 路径数量
- 权值总和
- DP 贡献之和

---

## 5.2 最大值聚合

暴力：

```
for(int j : candidate){
    if(property[j] == x){
        dp[i] = max(dp[i],dp[j] + 1);
    }
}
```

如果 `+1` 与具体 `j` 无关，可以维护：

```
mx[x] = max(mx[x],dp[j]);
```

查询：

```
dp[i] = mx[x] + 1;
```

典型形式：

```
找满足某种属性的状态中的最大 DP
```

---

## 5.3 最小值聚合

同理：

```
mn[x] = min(mn[x],dp[j]);
```

然后：

```
dp[i] = mn[x] + cost;
```

适用于：

- 最小代价
- 最短转移
- 最少操作数

---

## 5.4 数量聚合

如果只是判断或统计：

```
for(int j : candidate){
    if(property[j] == x){
        cnt++;
    }
}
```

可以直接维护：

```
cnt[x]++;
```

查询：

```
answer += cnt[x];
```

这其实就是频次数组、哈希表计数的本质。

---

## 5.5 布尔聚合

有时甚至不需要数量，只需要知道：

> 有没有？

暴力：

```
for(int j : candidate){
    if(property[j] == x){
        ok = true;
    }
}
```

可以维护：

```
exist[x] = true;
```

查询：

```
if(exist[x])
```

---

# 6. 聚合不只属于 DP

这是最重要的一点。

> **聚合不是一种 DP 技巧，而是一种非常通用的“消除重复搜索”思想。**

它会出现在很多地方。

---

## 6.1 前缀和就是一种聚合

假设经常查询：

```
区间 [l,r] 的总和
```

暴力：

```
for(int i=l;i<=r;i++){
    sum += a[i];
}
```

如果查询很多次，就重复扫描。

于是提前聚合：

```
pre[i] = a[1] + ... + a[i];
```

查询：

```
pre[r] - pre[l - 1]
```

本质就是：

```
重复枚举区间
        ↓
提前聚合前缀信息
        ↓
直接查询
```

所以前缀和其实就是最基础的聚合思想之一。

---

## 6.2 哈希表计数也是聚合

例如经典问题：

> 已经出现的数中，有多少个值等于 `x`？

暴力：

```
for(int j=1;j<i;j++){
    if(a[j] == x){
        cnt++;
    }
}
```

优化：

```
mp[a[j]]++;
```

查询：

```
mp[x]
```

也就是：

```
按照“数值”这个属性聚合出现次数
```

---

## 6.3 前缀和 + 哈希也是聚合

统计和为 `k` 的子数组：

\[ pre[r]-pre[l]=k \]

变形：

\[ pre[l]=pre[r]-k \]

对于每个当前前缀和 `pre[r]`，需要知道：

> 前面有多少个前缀和等于 `pre[r]-k`？

于是维护：

```
cnt[pre]++;
```

查询：

```
ans += cnt[pre - k];
```

这里就是：

> **按照“前缀和值”聚合历史状态。**

---

## 6.4 图论中也能聚合

比如对于每个点 `u`，经常需要：

> 所有邻居中颜色为 `c` 的贡献总和。

暴力：

```
for(int v : G[u]){
    if(color[v] == c){
        res += value[v];
    }
}
```

如果查询很多次，可以维护：

```
sum[u][c]
```

表示：

> `u` 的所有邻居中，颜色为 `c` 的贡献总和。

于是直接：

```
res = sum[u][c];
```

---

## 6.5 扫描线也是聚合思想

很多扫描线问题本质是：

```
随着扫描位置移动
维护当前有效元素的统计信息
```

例如：

```
当前有哪些区间覆盖这里？
当前有哪些点满足条件？
当前最大值是多少？
当前数量是多少？
```

本质也是：

> 不重新扫描所有历史对象，而是动态维护一个聚合结构。

---

## 6.6 单调栈 / 单调队列也有类似思想

滑动窗口最大值暴力：

```
for(每个窗口){
    扫一遍窗口找最大值
}
```

会重复扫描大量元素。

单调队列维护：

> 当前窗口中真正有可能成为最大值的候选。

虽然它不是严格意义上的“按 key 求和”，但思维非常相似：

> **不要每次重新搜索，把未来真正需要的信息动态维护下来。**

---

# 7. 聚合的核心模板

最典型的形式：

```
for(按照正确顺序枚举状态 i){
    int need = ...;

    dp[i] = query(agg,need);

    update(agg,property[i],dp[i]);
}
```

也就是：

```
查询历史聚合信息
        ↓
计算当前状态
        ↓
把当前状态加入聚合结构
```

这是一个非常值得熟悉的模式：

```
query → calculate → update
```

---

# 8. 为什么“顺序”非常重要

如果聚合结构存的是：

> 已经计算完成的状态

那么处理顺序必须保证：

> 查询时需要的状态已经加入聚合结构。

例如：

```
dp[i] = sum[property];
```

这里的 `sum` 应该包含哪些状态？

可能只允许：

```
j < i
```

那么就必须从左到右处理：

```
1 → 2 → 3 → ... → n
```

并且顺序必须：

```
query
calculate
update
```

而不能：

```
update
query
```

否则当前状态可能错误地使用自己。

这和前缀和哈希统计子数组时：

```
ans += cnt[pre - k];
cnt[pre]++;
```

必须先查再加，是完全一样的思想。

---

# 9. 排序可以人为制造“正确顺序”

有些问题原本没有天然的：

```
1 → 2 → 3
```

顺序。

但如果合法转移满足某个量严格变化：

```
value 增大
value 减小
时间增大
距离增大
长度增大
权值增大
```

那么可以：

```
先按这个量排序
```

然后再做：

```
query → calculate → update
```

因此有一类很常见的思考方式：

> [!tip] 当状态依赖关系很乱时  
> 找一个在合法转移过程中**严格单调的量**。
> 
> 如果找到了，可能就能通过排序人为建立 DP / 聚合的处理顺序。

---

# 10. 聚合以后，有时连原状态都不需要保存

假设原本：

```
dp[i]
```

计算出来之后，以后只会用于：

```
sum[property[i]] += dp[i];
```

再也不会有人直接查询：

```
dp[i]
```

那么可以直接：

```
int cur = query(...);
update(...,cur);
```

不用保存整个：

```
dp[]
```

也就是说：

```
完整状态
   ↓
计算出来
   ↓
立即压入聚合信息
   ↓
丢弃完整状态
```

这是一个很有价值的空间优化原则：

> [!important]  
> **只保存未来真正会查询的信息。**

---

# 11. 数据结构怎么选

聚合思想本身和具体数据结构无关。

根据 key 的特点选择即可。

---

## 数组

如果属性范围比较小：

```
sum[x]
```

优点：

- `O(1)`
- 常数小
- 最快

例如：

```
color <= 1e5
value <= 1e6
```

---

## map

如果 key 很大、很离散：

```
map<int,long long> sum;
```

复杂度：

\[ O(\log n) \]

优点：

- 稳定
- 自动有序

---

## unordered_map

```
unordered_map<int,long long> sum;
```

平均：

\[ O(1) \]

但：

- 常数较大
- 有哈希冲突
- 竞赛中有时需要防 hack

---

## 二维聚合

如果查询依赖两个属性：

```
sum[x][y]
```

也可以：

```
map<pair<int,int>,int> sum;
```

或者：

```
vector<map<int,int>> sum;
```

具体取决于状态结构。

---

# 12. 聚合什么时候最值得考虑

看到下面这些代码形态时应该敏感：

```
for(int i=...){
    for(int j=...){
        if(condition(i,j)){
            ...
        }
    }
}
```

尤其是：

```
if(property[j] == f(i))
```

这种形式。

因为它意味着：

> `i` 对 `j` 的要求，只取决于 `j` 的某个少量属性。

此时非常可能把：

```
枚举 j
```

变成：

```
查询 property 对应的桶
```

# 13. 一套实战检查流程

写出暴力后，可以按下面顺序检查。

> [!question] 第一步：重复了吗？  
> 同一批候选状态是不是被反复扫描？

如果是，继续。

> [!question] 第二步：真的需要知道候选是谁吗？  
> 我需要具体的 `j`，还是只需要它们的：
> 
> - 总和
> - 最大值
> - 最小值
> - 个数
> - 是否存在

如果只是统计量，继续。

> [!question] 第三步：我是根据什么条件筛选它们的？  
> 例如：
> 
> ```
> value
> color
> type
> difference
> remainder
> endpoint
> prefix sum
> ```

这个条件往往就是聚合 key。

> [!question] 第四步：能否动态维护？  
> 当前状态算出来以后，能否立即加入对应的桶？

如果可以，就很适合聚合。

> [!question] 第五步：处理顺序对吗？  
> 查询时需要的状态是否已经被加入聚合结构？

如果没有天然顺序，考虑：

```
排序
拓扑
从左到右
从右到左
按长度
按权值
```

# 14. 常见的抽象形式

## 形式一：等值条件

```
if(a[j] == x)
```

考虑：

```
sum[x]
```

---

## 形式二：差值条件

例如：

```
a[i] - a[j] = k
```

变成：

```
a[j] = a[i] - k
```

于是查询：

```
cnt[a[i] - k]
```

---

## 形式三：和条件

```
a[i] + a[j] = k
```

变成：

```
a[j] = k - a[i]
```

查询：

```
cnt[k - a[i]]
```

这就是 Two Sum 类思想。

---

## 形式四：模数条件

```
a[j] % k = r
```

聚合：

```
cnt[r]
```

---

## 形式五：类别条件

```
color[j] = c
```

聚合：

```
sum[c]
```

---

## 形式六：多个属性联合条件

```
color[j] = c
type[j] = t
```

聚合：

```
sum[c][t]
```

---

# 15. 聚合不一定能直接使用

聚合最适合这种形式：

```
candidate 是否可用
```

主要由少量属性决定。

如果转移是：

```
dp[i] = max(dp[i],dp[j] + cost(i,j));
```

而：

```
cost(i,j)
```

复杂依赖 `i,j` 两者，无法通过一个简单的属性表示，那么：

```
mx[property[j]]
```

可能会丢失必要信息。

这时候可能需要更高级的数据结构：

```
线段树
树状数组
单调队列
凸包优化
Li Chao Tree
分治
CDQ
```

其实这些高级优化，很多也可以理解成：

> **用更复杂的数据结构维护某种聚合信息。**

---

# 16. 从“简单聚合”到“数据结构优化”

可以把很多算法优化放在同一条线上理解：

```
暴力枚举历史状态
        ↓
简单按值聚合
        ↓
数组 / 哈希 / map
        ↓
需要区间统计
        ↓
前缀和 / 树状数组 / 线段树
        ↓
需要动态最大最小值
        ↓
单调队列 / multiset
        ↓
需要特殊函数最优值
        ↓
凸包优化 / Li Chao Tree
```

它们背后的共同思想往往都是：

> **不要每次重新扫描所有历史状态，而是维护未来查询真正需要的信息。**

---

# 17. 一个很重要的思维升级

初学时容易想：

```
我要如何更快地枚举这些状态？
```

更好的问题往往是：

```
我真的需要枚举它们吗？
```

例如：

```
for(int j : candidate){
    if(property[j] == x){
        ans += value[j];
    }
}
```

不要第一反应去优化循环。

应该先问：

> 如果我只需要这些元素的和，那为什么不直接保存这个和？

因此：

> [!success] 聚合思想的关键  
> 优化算法时，不要只想着“怎么更快地做同一件事”。
> 
> 有时候真正的优化是：
> 
> **发现这件事根本不需要做。**

---

# 18. 通用模板

## 求和

```
map<int,int> sum;

for(每个状态 i){
    int need = get_need(i);

    int cur = base + sum[need];

    sum[get_property(i)] += cur;
}
```

---

## 最大值

```
map<int,int> mx;

for(每个状态 i){
    int need = get_need(i);

    int cur = mx[need] + cost;

    mx[get_property(i)] = max(mx[get_property(i)],cur);
}
```

---

## 计数

```
map<int,int> cnt;

for(每个元素 x){
    ans += cnt[get_need(x)];

    cnt[get_property(x)]++;
}
```

核心始终是：

```
query
  ↓
calculate
  ↓
update
```

## 19. 最后总结

> **按属性聚合**
> 
> 当算法中出现大量：
> 
> ```
> 枚举候选
>     ↓
> 判断某个属性
>     ↓
> 统计符合条件的候选
> ```
> 
> 可以考虑维护：
> 
> ```
> 属性 → 聚合结果
> ```
> 
> 聚合结果可能是：
> 
> - 和
> - 最大值
> - 最小值
> - 数量
> - 是否存在
> 
> 从而把：
> 
> ```
> 每次重新寻找答案
> ```
> 
> 变成：
> 
> ```
> 状态产生时维护答案
> 查询时直接读取
> ```

最值得记住的两个问题：

> **> **1. 我真的需要枚举这些候选吗？****
> 
> **2. 我未来查询它们时，真正关心的属性是什么？**

如果第二个问题的答案很简单，那么很可能就存在：

\[ \boxed{\text{按属性聚合}} \]

这类优化。

最终核心思想可以浓缩成一句：

> **把未来会反复搜索的信息，在它产生的时候就按照查询条件整理好。**
